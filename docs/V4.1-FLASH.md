# DeepSeek-V4.1-Flash on 8× RTX PRO 6000 — analysis, bring-up and results

Test date: 2026-11-01, same node as the V4-Flash test (LKE plan `g3-gpu-rtxpro6000-blackwell-8`). Facts about the
model come from the model card, the Hugging Face API and the vLLM release notes (sources at the end).
Raw data: `results/v41-*`. Logs: `logs/*v41*`.

## 0. Summary

| Question | Answer |
|---|---|
| Does V4.1-Flash run on RTX PRO 6000 (SM120) with the stock vLLM 0.32.0 image? | **No** — crashes at start-up (`block_kv == 32 or block_kv == 64`, §5). Known upstream issue, fix not released yet |
| Does it run with the pending fix? | **Yes** — vLLM 0.32.0 + [PR #60762](https://github.com/vllm-project/vllm/pull/60762) (4 lines) + FlashInfer 0.7.2.post1, applied at container start (§6) |
| Are the answers correct on that stack? | **Yes** — GSM8K 245/250 (98%); two facts hidden in a **1.01 M-token** document both found; same with DSpark (244/250) |
| Layout | TP=8 only (510 GB does not fit in 4 GPUs) |
| One user, 120k prompt | TTFT **8.9 s** (V4: 14.1 s TP=8, 13.4 s TP=4) |
| One user, 1M-token prompt | TTFT **91 s** (V4: 217–223 s) |
| Generation speed, one user | **78 tok/s flat from 8k to 1M** (V4 TP=4: 98 → 51; V4 TP=8: 74 → 42) |
| With DSpark speculative decoding, real text | **155 tok/s** for one user (+97%), 1,351 tok/s with 64 users (+27%) |
| Coding agent with prefix caching (context 30k → 86k) | **~0.55 s TTFT per turn** after the first, from 1 to 16 parallel agents |
| Peak output, 10k random prompts, 128 users | 540 tok/s (V4 TP=8: 423; V4 2×TP=4: 803) |
| Failed requests | 0 |

**For developers, V4.1 is the better model on this node** — much faster prompt processing, flat decode speed at any
context, and with prefix caching an agent turn costs ~0.5 s regardless of how much context it carries. For high-volume
short chat, V4 as 2 replicas × TP=4 still delivers more total tokens per node. **The catch: V4.1 needs an
unreleased fix on SM120**, so it is a PoC configuration until vLLM ships PR #60762 (§9).

## 1. Is DeepSeek-V4-Flash a model for developers?

It is a general-purpose model (chat, reasoning, tool use), not a code-only model, but coding and agentic coding are
among its strongest uses: third-party pages that reproduce the model card list SWE-bench Verified around 79 for
V4-Flash with thinking on (check the official card before quoting it). How well it fits depends on the workload:

| Developer workload | Typical request | What the V4-Flash test shows | Fit |
|---|---|---|---|
| Chat in the IDE (explain / write / review code) | 1k–10k prompt | TTFT ~1 s, 98 tok/s (161 with MTP on real text); ~16–30 concurrent requests per node | Good |
| Coding agent (Claude Code-style, Cline, OpenCode) | 30k–120k context per turn, many turns | Without prefix caching each turn pays full TTFT: 3.3 s at 32k, 6.3 s at 60k, 13.4 s at 120k; ~2–4 agents per node | Viable; prefix caching measured on V4.1 (§7.4) |
| Whole-repository analysis | 240k–1M prompt | TTFT 30 s to 3.6 min | Batch / async |
| Tab autocomplete (fill-in-the-middle) | < 2k prompt, < 200 ms | Not measured; wrong tool | Use a small code model |

## 2. What V4.1-Flash changes

| | V4-Flash (tested) | V4.1-Flash |
|---|---|---|
| Released | 2026-04-22 | 2026-09-10; update "1017" on 2026-10-17 |
| Hugging Face architecture | `DeepseekV4ForCausalLM` | `DeepseekV41ForCausalLM` (Causal Encoder-Decoder) |
| Checkpoint size | 159.6 GB | **510.3 GB** (476 GiB) |
| Parameters | 284 B total, 13 B active | 552 B backbone + 196 B Engram memory; **8 B active in prefill, 16 B in decode** |
| KV cache | baseline | global KV per token **~4× smaller** (model card, Fig. 1b); persistent KV (incl. sliding-window) **~1/8** with SWA bounded replay |
| Input | text | text **and images** |
| Speculative decoding | 1 MTP layer | DSpark (semi-autoregressive draft) |
| Reasoning effort | modes | continuous setting, integer 1–100 |
| Prompt format | encoder as code (`--tokenizer-mode deepseek_v4`) | `--tokenizer-mode deepseek_v41`; `encoding.py` reference + `chat_template.jinja` in the repo; [deepseek-recipe](https://github.com/deepseek-ai/deepseek-recipe) for production |
| Experts per MoE layer | — | 1 shared + 384 routed, 6 active |
| Weights | FP4 experts + FP8 | FP4 experts + FP8 (block 32×32, ue8m0 scales) |
| License | MIT | MIT |
| DeepSeek API | discontinued; the old name redirects to V4.1 | current model |
| vLLM support | native on SM120 in v0.32.0 (tested) | since v0.30.0; on SM120 needs PR #60762 + FlashInfer ≥ 0.7.1 (tested, §6) |

## 3. Why it was worth testing for developers

- **The bottleneck measured on V4 was prefill (TTFT).** V4.1 activates only 8 B parameters per token in prefill
  (13 B in V4). → Confirmed: prefill ~13k tok/s vs ~9k tok/s (§7.1).
- **Smaller KV cache.** → Confirmed: 10.7 M tokens of KV cache with TP=8, vs 6.26 M for V4 on the same 8 GPUs.
- **It is the model the DeepSeek API serves today**, with the "1017" update aimed at coding and agents.

## 4. Constraints on this node (8× RTX PRO 6000, 96 GB each, PCIe, two CPU sockets)

| Constraint | Outcome |
|---|---|
| **Only TP=8 fits** (510 GB > 4 × 96 GB) | 47.6 GiB of weights per GPU + 11.8 GiB of Engram tables per rank in pinned host RAM (vLLM default `EngramConfig.cpu_offload=True`, 94 GiB of the node's 1.4 TB). The 2×TP=4 layout that won for V4 is impossible |
| All-reduce over PCIe across two sockets | Same as V4 TP=8: PYNCCL only (custom all-reduce disabled for > 2 PCIe GPUs); GPUs at ~240 W average of 600 W |
| SM120 kernels | Attention runs on `FLASHINFER_MLA_SPARSE_DSV41`; MoE on `DEEPGEMM_MXFP4`; KV `fp8_ds_mla`, 64-token blocks (after the fix) |
| Download / start-up | 476 GiB in **318 s** (~1.6 GB/s); server ready in **~5 min** (weights 22 s, engine init 158 s) |

## 5. First attempt: stock vLLM 0.32.0 fails on SM120

| Step | Result |
|---|---|
| Download (Job [k8s/06-download-model-v41.yaml](../k8s/06-download-model-v41.yaml)) | 476 GiB in 318 s |
| vLLM 0.32.0, TP=8 ([k8s/20-vllm-dsv41-flash-tp8.yaml](../k8s/20-vllm-dsv41-flash-tp8.yaml)) | Weights loaded; Engram offloaded; TileLang kernels compiled |
| CUDA-graph memory profiling (~2 min after start) | **Crash**: `Assertion error (csrc/apis/attention.hpp:411): block_kv == 32 or block_kv == 64` in DeepGEMM `get_paged_mqa_logits_metadata` (V4.1 sparse indexer) |

Log: [logs/startup-v41-tp8-stock-fail.log](../logs/startup-v41-tp8-stock-fail.log).

**Cause.** In vLLM 0.32.0 the V4.1 indexer and FlashInfer sparse-MLA backends declare 128-token KV blocks on every
GPU except Hopper (`[64 if family(90) else 128]`). The SM120 decode kernels only accept 32- or 64-token blocks.
B200 (SM100) and H100/H200 (SM90) work; RTX PRO 6000 (SM120) and GB10 (SM121) do not. Known upstream:

| Upstream item | State (2026-11-01) | What it says |
|---|---|---|
| [vLLM PR #60762](https://github.com/vllm-project/vllm/pull/60762) | open, approved, needs rebase | Declares 64-token blocks on SM12x; validated on 8× RTX PRO 6000 (GSM8K 89–91%); **requires FlashInfer ≥ 0.7.1rc5** (image ships 0.7.0.post1) |
| [vLLM issue #59203](https://github.com/vllm-project/vllm/issues/59203) | open | Same failure on RTX PRO 6000 |
| [vLLM issue #56700](https://github.com/vllm-project/vllm/issues/56700) | open | Field report, 8× RTX PRO 6000: works only with patched builds; pitfalls include **silent numerical corruption at ≥100k context** with a wrong FP8 KV layout, CUDA-graph crashes, DeepGEMM autotune hangs |
| [vLLM issue #56892](https://github.com/vllm-project/vllm/issues/56892) | open | Very low decode throughput on SM120 TP=8 when CUDA graphs must be disabled |
| [vLLM issue #58910](https://github.com/vllm-project/vllm/issues/58910) | open | Xid 31 illegal memory access during long prefill on SM120 |
| [vLLM PR #57292](https://github.com/vllm-project/vllm/pull/57292) | open | Fail fast on SM120 when FlashInfer lacks runtime page sizes |
| [vLLM issue #64192](https://github.com/vllm-project/vllm/issues/64192) | open | Request for an official RTX PRO 6000 recipe for V4.1-Flash |

## 6. The working stack (patched, not yet released upstream)

Manifest: [k8s/21-vllm-dsv41-flash-tp8-patched.yaml](../k8s/21-vllm-dsv41-flash-tp8-patched.yaml) (variants:
[22](../k8s/22-vllm-dsv41-flash-tp8-patched-prefix.yaml) prefix caching on,
[23](../k8s/23-vllm-dsv41-flash-tp8-patched-prefix-dspark.yaml) prefix caching + DSpark). The stock
`vllm/vllm-openai:v0.32.0` image runs a start script from a ConfigMap that:

1. Replaces FlashInfer 0.7.0.post1 by **0.7.2.post1**: `flashinfer-python`, the `flashinfer-jit-cache` shim and
   `flashinfer-jit-cache-sm120f` (cu130), all `--no-deps` (the image already has every dependency at the right
   version). `flashinfer-cubin` has no 0.7.x release and is removed.
2. Applies the source part of **PR #60762**
   ([patches/vllm-pr60762-sm120-64-token-blocks.diff](../patches/vllm-pr60762-sm120-64-token-blocks.diff)):
   `return [64]` on SM12x for `DeepseekV41IndexerBackend` and `DeepseekV4FlashInferMLASparseBackend`.
3. `exec vllm serve` with `--tokenizer-mode/--reasoning-parser/--tool-call-parser deepseek_v41`,
   `--enable-auto-tool-choice`, `--max-model-len 1048576`, TP=8.

The wheels and the diff were pre-staged on the node disk next to the weights, so start-up downloads nothing; the node
itself is not modified. vLLM then logs `Setting kv cache block size to 64 for FLASHINFER_MLA_SPARSE_DSV41/
DEEPSEEK_SPARSE_SWA/DEEPSEEK_V41_INDEXER/CompressorBackend` and starts with CUDA graphs on.

## 7. Results

### 7.1 Correctness first

Because of the corruption reports on SM120, quality was checked before any timing
([scripts/gsm8k_eval.py](../scripts/gsm8k_eval.py), [scripts/needle.py](../scripts/needle.py)):

| Check | Without speculation | With DSpark k=3 |
|---|---|---|
| GSM8K, first 250 test questions, temperature 0, thinking on | **245 / 250 (98.0%)** | **244 / 250 (97.6%)** |
| Two facts hidden at 50% and 80% depth, ~108k-token document | both found (9.6 s) | both found (8.8 s) |
| Same, ~534k tokens | both found (44.6 s) | both found (44.2 s) |
| Same, **~1.01 M tokens** | **both found** (92.6 s) | not run |

The one-request time for the 1M document (93 s including the answer) is less than half of V4's TTFT alone (217 s).

### 7.2 One user, by prompt length (random prompts, 512 output tokens, prefix caching off)

| Prompt | V4.1 TTFT | V4.1 tok/s | V4 TP=8 TTFT / tok/s | V4 TP=4 TTFT / tok/s |
|---:|---:|---:|---:|---:|
| 8k | **0.60 s** | 78 | 0.87 s / 74 | 0.82 s / 98 |
| 10k | **0.77 s** | 78 | 1.10 s / 74 | 1.03 s / 98 |
| 32k | **2.4 s** | 78 | 3.5 s / 73 | 3.3 s / 96 |
| 60k | **4.5 s** | 78 | 6.7 s / 71 | 6.3 s / 93 |
| 120k | **8.9 s** | 78 | 14.1 s / 67 | 13.4 s / 90 |
| 240k | **18.4 s** | 78 | 31.1 s / 63 | 29.8 s / 83 |
| 512k | **41.8 s** | 78 | 82.8 s / 54 | 79.8 s / 68 |
| **1M** | **90.8 s** | **78** | 222.7 s / 42 | 216.7 s / 51 |

- **Prefill ~13.4k tok/s at 120k, ~11k tok/s at 1M** (V4: ~9k and ~4.6k). TTFT is 1.5× lower at 120k and
  **2.4× lower at 1M**.
- **Decode is completely flat: 77.6–78.2 tok/s from 8k to 1M** (ITL p50 12.8–13.4 ms). V4's decode slowed with
  context; V4.1's does not. At short context V4 on 4 GPUs is still faster per user (98 tok/s).

### 7.3 Concurrency (whole node, 8 GPUs)

10k random prompts:

| Users | V4.1 TTFT p50 | V4.1 tok/s per user | V4.1 total | V4 TP=8 total | V4 2×TP=4 total |
|---:|---:|---:|---:|---:|---:|
| 1 | 0.8 s | 78 | 70 | 64 | — |
| 2 | 1.1 s | 70 | 122 | 107 | — |
| 4 | 2.2 s | 56 | 182 | 167 | — |
| 8 | 2.7 s | 39 | 256 | 239 | — |
| 16 | 3.0 s | 25 | 344 | 303 | 519 |
| 32 | 3.0 s | 14 | 417 | 347 | 637 |
| 64 | 3.0 s | 7.8 | 469 | 391 | 713 |
| 128 | 3.6 s | 4.5 | **540** | 423 | **803** |

60k / 120k prompts (prefix caching off — every request processes its whole prompt):

| Prompt | Users | V4.1 TTFT p50 | V4.1 tok/s per user | V4 2×TP=4 TTFT / tok/s per user |
|---:|---:|---:|---:|---:|
| 60k | 2 | 6.8 s | 57 | 6.4 s / 95 |
| 60k | 4 | 9.7 s | 32 | 9.7 s / 58 |
| 60k | 8 | 9.6 s | 15 | 15.0 s / 31 |
| 120k | 2 | 13.4 s | 46 | 13.4 s / 91 |
| 120k | 4 | 19.6 s | 22 | 20.0 s / 40 |
| 120k | 8 | 18.7 s | 8.5 | 30.7 s / 18 |

Under load, one TP=8 engine shares its decode among all requests, while V4 splits them over two independent 4-GPU
engines: **for many concurrent cold long prompts, V4 2×TP=4 still gives each user more tokens per second.** ITL p99
of ~600 ms appears whenever a long prefill runs alongside decodes (chunked prefill), as with V4.

### 7.4 Coding-agent simulation (prefix caching on)

[scripts/agent_sim.py](../scripts/agent_sim.py): each session is 10 turns; turn 1 sends 30k tokens (system prompt +
files), every next turn re-sends the whole conversation + the previous 256-token answer + 6k new tokens (tool
output), up to 86k tokens. Every session uses its own content, so a turn can only reuse its own earlier turns.

| Parallel agents | TTFT turn 1 (cold, 30k) | **TTFT later turns p50 / p90** | tok/s per agent | Turns per minute (node) |
|---:|---:|---:|---:|---:|
| 1 | 2.2 s | **0.54 / 0.55 s** | 78 | 15 |
| 2 | 3.4 s | **0.55 / 0.57 s** | 65 | 25 |
| 4 | 5.6 s | **0.56 / 1.02 s** | 46 | 35 |
| 8 | 10.1 s | **0.56 / 1.03 s** | 31 | 47 |
| 16 | 18.7 s | **0.57 / 1.04 s** | 20 | 60 |

- **Prefix caching changes the picture for agents.** Without it, an 86k-token turn would cost ~6.4 s of TTFT; with
  it, only the ~6k new tokens are processed and the turn starts in **~0.55 s at any context size and up to 16 agents**.
- The cold first turn grows with the number of agents starting at the same moment (they queue for prefill); in real
  use agents start at different times.
- With 16 agents each still gets ~20 tok/s; with 8, ~31 tok/s.
- Not measured on V4 with prefix caching (V4 runs had it off); V4's cold-turn numbers are in §1.

With DSpark the same simulation ran at 205 / 85 / 27 tok/s per agent (1 / 4 / 16 agents) with the same ~0.5–0.6 s
TTFT, but these decode numbers are **optimistic**: the simulation uses random tokens and `ignore_eos`, and the model's
output on random input is repetitive and easy to draft. Use the real-text numbers below for speculation.

### 7.5 DSpark speculative decoding on real text (Spec-Bench, prefix caching on)

Same 480-question set and seed as the V4 MTP test ([scripts/bench-realtext.sh](../scripts/bench-realtext.sh)),
`--speculative-config {"method":"dspark","num_speculative_tokens":3}`:

| Users | tok/s per user, no spec | tok/s per user, DSpark | total, no spec | total, DSpark | Gain (total) | Acceptance | Tokens per step |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 79 | **155** | 78 | 139 | **+79%** (per user +97%) | 49% | 2.47 |
| 4 | 60 | **100** | 222 | 370 | **+66%** | 50% | 2.50 |
| 16 | 38 | **50** | 549 | 676 | **+23%** | 49% | 2.48 |
| 64 | 18 | **25** | 1,061 | **1,351** | **+27%** | 49% | 2.46 |

- DSpark proposes 3 tokens per step; about half are accepted, so each step yields ~2.5 tokens.
  Per-position acceptance: 75% / 54% / 37% (vLLM metrics, [spec-metrics.txt](../results/v41-dspark-realtext/spec-metrics.txt)).
- **One user doubles to ~155 tok/s** — the same as V4 with MTP on 4 GPUs (161), on a model with a stronger agent
  profile. Quality unchanged (GSM8K 244/250, needles found).
- For comparison, V4 per 4-GPU replica on the same questions: 109 → 161 tok/s (1 user), 1,130 → 1,527 tok/s (64 users).
  Per node, V4 (two replicas) remains the higher-throughput option for short chat.
- k > 3 not tried (k=7 reported to corrupt output on SM120 in the PR #60762 thread).

### 7.6 GPU telemetry and memory

| Item | V4.1 TP=8 | V4 TP=8 |
|---|---|---|
| Weights per GPU | 47.6 GiB (+ 11.8 GiB Engram per rank in host RAM) | 19.8 GiB |
| KV cache capacity | **10.7 M tokens** (10.1 M with DSpark) — 1M-token requests that fit at once: 10.2 | 6.26 M |
| GPU power, busy (avg / max) | ~237 W / 335 W | ~270 W / 468 W |
| Max GPU temperature | 56 °C | 63 °C |

As with V4 TP=8, the GPUs show 100% SM busy at well under half their 600 W limit: the all-reduce over PCIe between
the two CPU sockets bounds the speed.

## 8. For developers: V4.1 or V4 on this node?

| Developer workload | Better choice on 8× RTX PRO 6000 | Why (measured) |
|---|---|---|
| Coding agents (Claude Code-style), multi-turn, 30k–100k+ context | **V4.1 + prefix caching (+ DSpark)** | ~0.55 s per turn up to 16 agents; flat 78 tok/s decode (≈155 with DSpark on real text); 10.7 M KV tokens |
| Very long documents / whole repositories (240k–1M) | **V4.1** | TTFT 18 s at 240k, 91 s at 1M (V4: 30 s and 217 s); decode still 78 tok/s at 1M; 1M-needle correct |
| IDE chat, short prompts, many users | **V4, 2 × TP=4 + MTP** | ~2× the node throughput (two independent engines); 98–161 tok/s per user |
| Tab autocomplete | Neither | Use a small code model next to it |

Capacity per node (estimates from the measurements above, real usage patterns will move them):

- **V4.1 coding agents:** ~8 agents working at the same time at ~30 tok/s each (16 at ~20 tok/s), turns starting in
  ~0.5 s. Agents spend part of their time waiting for tools and the developer, so the number of developers served is
  higher than the number of agents generating at any moment.
- **V4 IDE chat:** ~16–30 concurrent requests at ≥ 25 tok/s (RESULTS §6).

## 9. Caveats

- **Unreleased fix.** The stack is vLLM 0.32.0 + PR #60762 + FlashInfer 0.7.2.post1. It passed GSM8K and the 1M
  needle test and ran ~1.5 h with 0 failed requests, but it is not an official vLLM build. Wait for a vLLM release
  that includes PR #60762 (and a matching FlashInfer) before production, then re-run [scripts/gsm8k_eval.py](../scripts/gsm8k_eval.py)
  and [scripts/needle.py](../scripts/needle.py).
- **Not tested:** image input; tool calling end-to-end with an agent client; reasoning-effort levels; DSpark k > 3;
  `VLLM_ALLREDUCE_USE_FLASHINFER_PCIE_IPC=1` (reported +12% decode on the same hardware, vLLM #56700).
- **Agent simulation uses random tokens**, so it measures latency and cache behaviour, not answer quality or real
  draft acceptance.
- Single node: production should use at least two GPU nodes.
