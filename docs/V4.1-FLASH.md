# DeepSeek-V4.1-Flash — why test it, and what to expect on this node

Written 2026-10-31, before testing V4.1-Flash. Facts come from the model card, the Hugging Face API and the vLLM
release notes (sources at the end); expectations are marked as such. Test results will be added to
[RESULTS.md](RESULTS.md) when the run is done.

## 1. Is DeepSeek-V4-Flash a model for developers?

It is a general-purpose model (chat, reasoning, tool use), not a code-only model, but coding and agentic coding are
among its strongest uses: third-party pages that reproduce the model card list SWE-bench Verified around 79 for
V4-Flash with thinking on (check the official card before quoting it). How well it fits depends on the workload:

| Developer workload | Typical request | What the V4-Flash test shows | Fit |
|---|---|---|---|
| Chat in the IDE (explain / write / review code) | 1k–10k prompt | TTFT ~1 s, 98 tok/s (161 with MTP on real text); ~16–30 concurrent requests per node | Good |
| Coding agent (Claude Code-style, Cline, OpenCode) | 30k–120k context per turn, many turns | Without prefix caching each turn pays full TTFT: 3.3 s at 32k, 6.3 s at 60k, 13.4 s at 120k; ~2–4 agents per node | Viable, needs a prefix-caching test |
| Whole-repository analysis | 240k–1M prompt | TTFT 30 s to 3.6 min | Batch / async |
| Tab autocomplete (fill-in-the-middle) | < 2k prompt, < 200 ms | Not measured; wrong tool | Use a small code model |

Developers per node (estimate, not measured): IDE chat with 10–20% of developers active at peak → ~80–300 developers;
coding agents keep a request in flight almost all the time → ~2–4 agents running at once with long context. The
agent figures are a worst case because prefix caching was off in the benchmark.

## 2. What V4.1-Flash changes

| | V4-Flash (tested) | V4.1-Flash |
|---|---|---|
| Released | 2026-04-22 | 2026-09-10; update "1017" on 2026-10-17 |
| Hugging Face architecture | `DeepseekV4ForCausalLM` | `DeepseekV41ForCausalLM` (Causal Encoder-Decoder) |
| Checkpoint size | 159.6 GB | **510.3 GB** |
| Parameters | 284 B total, 13 B active | 552 B backbone + 196 B Engram memory; **8 B active in prefill, 16 B in decode** |
| KV cache | baseline | global KV per token **~4× smaller** (model card, Fig. 1b); persistent KV (incl. sliding-window) **~1/8** with SWA bounded replay |
| Input | text | text **and images** |
| Speculative decoding | 1 MTP layer | DSpark (semi-autoregressive draft) |
| Reasoning effort | modes | continuous setting, integer 1–100 |
| Prompt format | encoder as code (`--tokenizer-mode deepseek_v4`) | `encoding.py` reference + `chat_template.jinja` in the repo; [deepseek-recipe](https://github.com/deepseek-ai/deepseek-recipe) for production |
| Experts per MoE layer | — | 1 shared + 384 routed, 6 active |
| Weights | FP4 experts + FP8 | FP4 experts + FP8 (block 32×32, ue8m0 scales) |
| License | MIT | MIT |
| DeepSeek API | discontinued; the old name redirects to V4.1 | current model |
| vLLM support | v0.2x onward; native on SM120 in v0.32.0 (tested) | since v0.30.0; tuned kernels listed for SM100 (B200), not for SM120 |

Sizes and architectures from the Hugging Face API (`/api/models/<id>?blobs=true` and `config.json`); the rest from
the V4.1-Flash model card and the vLLM v0.30.0–v0.32.0 release notes.

## 3. Why it is worth testing for developers

- **The bottleneck we measured was prefill (TTFT).** V4.1 activates only 8 B parameters per token in prefill
  (13 B in V4), which should shorten TTFT on long prompts — the main cost of coding agents. *Expectation.*
- **KV cache 4–8× smaller** (global KV per token ~4×, persistent KV ~8×) → more long sessions in memory at the same
  time. *Expectation.*
- **It is the model the DeepSeek API serves today**, with the "1017" update aimed at coding and agents. If the offer
  should match the API, V4.1 is the model to size.

## 4. Risks on this node (8× RTX PRO 6000, 96 GB each, PCIe, two CPU sockets)

| Risk | Detail |
|---|---|
| **Only TP=8 fits** | 510 GB does not fit in 4 GPUs (384 GB), so the 2×TP=4 layout that won for V4 is impossible. TP=8 was the slow layout on this node (no NVLink, all-reduce across sockets). The 8 B-active prefill may offset part of it. |
| **Little KV memory left** | ~768 GB × 0.9 − 510 GB ≈ 180 GB for KV and activations across 8 GPUs (V4 had 8.7 M tokens of KV per node). The 4–8× smaller KV should compensate; to be measured. |
| **SM120 kernels** | vLLM's V4.1 optimizations (FlashMLA mega attention, NVFP4 compressed KV) are listed for SM100. On SM120 vLLM may fall back to slower kernels or fail. |
| **Download and start-up** | 510 GB: ~7 min at the 1.2 GB/s seen for V4; start-up longer than V4's 7.5 min. Node disk must hold 510 GB (checked before download). |

## 5. Test plan

1. Same random-prompt suite as V4 on TP=8: 1 user 8k → 1M, 10k with 1–128 users, 60k/120k with 2–8 users.
2. Agent-like test: multi-turn sessions with a growing shared prefix, prefix caching **on**, TTFT per turn.
3. Short image-input check.
4. Document, commit, delete everything created.

## 6. Result of the first attempt (2026-11-01): does not start on stock vLLM 0.32.0 on SM120

| Step | Result |
|---|---|
| Download (Job [k8s/06-download-model-v41.yaml](../k8s/06-download-model-v41.yaml)) | 476 GiB in **318 s** (~1.6 GB/s) |
| vLLM 0.32.0, TP=8 ([k8s/20-vllm-dsv41-flash-tp8.yaml](../k8s/20-vllm-dsv41-flash-tp8.yaml)) | Weights loaded; Engram tables offloaded to pinned host RAM (**11.8 GiB per rank**, 94 GiB total); TileLang kernels compiled |
| CUDA-graph memory profiling (~2 min after start) | **Crash**: `Assertion error (csrc/apis/attention.hpp:411): block_kv == 32 or block_kv == 64` in DeepGEMM `get_paged_mqa_logits_metadata` (V4.1 sparse indexer) |

Log: [logs/startup-v41-tp8-stock-fail.log](../logs/startup-v41-tp8-stock-fail.log).

**Cause.** In vLLM 0.32.0 the V4.1 indexer and sparse-MLA backends declare 128-token KV blocks on every GPU except
Hopper (`[64 if family(90) else 128]`). The DeepGEMM / FlashInfer decode kernels built for SM120 only accept 32- or
64-token blocks. B200 (SM100) and H100/H200 (SM90) work; RTX PRO 6000 (SM120) and GB10 (SM121) do not. It is a known,
open upstream problem, not a configuration error:

| Upstream item | State (2026-11-01) | What it says |
|---|---|---|
| [vLLM PR #60762](https://github.com/vllm-project/vllm/pull/60762) | open, approved, needs rebase | Declares 64-token blocks on SM12x; validated on 8× RTX PRO 6000 (GSM8K 89–91%); **requires FlashInfer ≥ 0.7.1rc5** (image ships 0.7.0.post1) |
| [vLLM issue #59203](https://github.com/vllm-project/vllm/issues/59203) | open | Same failure on RTX PRO 6000 |
| [vLLM issue #56700](https://github.com/vllm-project/vllm/issues/56700) | open | Field report, 8× RTX PRO 6000: works only with patched builds; pitfalls include **silent numerical corruption at ≥100k context** with a wrong FP8 KV layout, CUDA-graph crashes, DeepGEMM autotune hangs |
| [vLLM issue #56892](https://github.com/vllm-project/vllm/issues/56892) | open | Very low decode throughput on SM120 TP=8 when CUDA graphs must be disabled |
| [vLLM issue #58910](https://github.com/vllm-project/vllm/issues/58910) | open | Xid 31 illegal memory access during long prefill on SM120 |
| [vLLM PR #57292](https://github.com/vllm-project/vllm/pull/57292) | open | Fail fast on SM120 when FlashInfer lacks runtime page sizes |
| [vLLM issue #64192](https://github.com/vllm-project/vllm/issues/64192) | open | Request for an official RTX PRO 6000 recipe for V4.1-Flash |

Field numbers reported in #56700 on the same hardware (SGLang, patched, TP=8/EP=8 — not measured here): prefill
~6.8k tok/s at 128k, prefix-cache hit of a 112k prefix in 0.34 s, decode 94–134 tok/s with DSpark speculative decoding
and ~36 tok/s without it; only TP8/EP8 starts (vision path rejects DP).

**What this means today.** V4.1-Flash on RTX PRO 6000 needs an unreleased vLLM fix plus a newer FlashInfer, and the
community reports correctness and stability problems on SM120 that must be checked (long-context needle test,
GSM8K) before any production use. V4-Flash, by contrast, runs on the stock vLLM 0.32.0 image.
